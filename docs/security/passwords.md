# Password storage

Policy and implementation notes for credentials in the TypeScript API. The Python app never stored credentials; this is the first auth surface in the repo.

## What the server stores

Argon2id PHC strings, produced by `apps/api/src/auth/password.ts`:

```
$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>
```

| Parameter | Value | Why |
|---|---|---|
| `type` | `argon2id` | Hybrid of the data-independent and data-dependent variants; OWASP's first recommendation. |
| `m` (memory) | 19 456 KiB | 19 MiB per hash. Memory-hardness is what makes GPU/ASIC cracking expensive. |
| `t` (time) | 2 | Two passes over that memory. |
| `p` (parallelism) | 1 | The API process is single-purpose; more lanes do not help here. |

These are the **floor**, not a tuning target. Raising them in `ARGON2_OPTIONS` does not invalidate stored hashes: `needsUpgrade()` reports `true` and the login path re-hashes on the next successful sign-in.

The salt is generated by `argon2` per call, 16 bytes, embedded in the PHC string. Two hashes of the same password never match — that is expected, not a bug.

## Pepper

`ARGON2_PEPPER` is a 64-character hex string (32 bytes) validated at boot by `apps/api/src/env.ts`. It is concatenated with the password **before** the KDF, so a stolen database alone cannot be attacked offline without also stealing the pepper.

Rules:

- It lives only in the process environment. Never in a commit, a log line, a queue payload, or an error message.
- It is passed as an argument (`Buffer`), never held in module state except the cached dummy hash (which contains no plaintext).
- Rotating it invalidates every stored hash. The rotation procedure is: new pepper in the secret store → deploy → force a password reset for every user, **or** keep the old pepper for verification and re-hash on login (two-pepper window). There is no transparent migration.

`verifyPassword` reads the pepper from the caller, so #120 is responsible for wiring `Buffer.from(env.ARGON2_PEPPER, "hex")` in exactly one place.

## Account enumeration

`POST /auth/login` must behave identically for existing and non-existing e-mails:

- Unknown e-mail → verify against a cached dummy hash (`verifyDummyPassword`), not an early return.
- Same status code, same body, same timing band.
- `auth-password.test.ts` measures the dummy path against a real verification; both run the same KDF.

## Throttling

`apps/api/src/auth/throttle.ts` is a sliding window keyed by e-mail and by IP:

- 5 failures inside 15 minutes → the next attempt is rejected with `429` and `Retry-After`.
- A successful login resets the e-mail bucket.
- State is in-memory and per process. That is a deliberate limit: a second API instance has its own counters. Move to Redis when the API runs more than one replica.

## Policy

Enforced by `POST /auth/register` (`AuthSession.#assertPasswordPolicy`):

- Minimum length 12 characters; maximum 128; no composition rules (no forced uppercase/digit/symbol).
- Reject a password equal to the e-mail local part.
- A top-10 000 common-password denylist is **not** bundled yet; if added, it belongs in the same policy function so login and future change-password routes share it.
- Allow and encourage passphrases; do not truncate at 72 bytes (that is a bcrypt limit, not Argon2's).
- Do **not** force periodic rotation. NIST SP 800-63B recommends rotation only on evidence of compromise.

## Legacy hashes

`needsUpgrade()` returns `true` for anything that is not a current Argon2id PHC string, including bcrypt and unreadable values. On a successful Argon2id login the route already re-hashes when `needsUpgrade()` says so.

`verifyPassword` itself only understands Argon2id and returns `false` for bcrypt. There is no bcrypt verifier in the Node app and the Python app never stored credentials, so no legacy rows exist. If one ever appears, the intended flow is:

1. Verify with the legacy algorithm.
2. On success, re-hash with `hashPassword` and replace `users.password_hash` in the same transaction.
3. Never write a new bcrypt hash.
